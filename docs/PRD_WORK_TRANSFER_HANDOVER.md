# CATV 업무관리 — 지역 기반 업무이관 PRD

## 1. 목적

현장 사진으로 접수되는 업무 내용을 텍스트로 변환(OCR)해 지역별 업무이관으로 등록하고, 담당 지역의 현장 매니저가 현장처리를 기록한 뒤 권한자가 최종 완료하는 업무 흐름을 제공한다.

기존 `업무이관 관리` 화면과 업무이력 구조는 유지한다. 목록의 핵심 열은 **날짜, 지역, 주소, 처리내용, 상태/완료**로 단순화하고, 상세 화면에서 사진·OCR 원문·처리이력 전체를 확인한다.

## 2. 범위

### 포함

- 지역 단위 업무이관 등록·수정·조회·현장처리·최종완료
- 사진 첨부 및 OCR 텍스트 추출, 사용자의 검수·수정 후 저장
- 긴급 건 표시 및 목록 우선 정렬
- 권한과 지역에 따른 서버·화면 단위 접근 제어
- 미완료/현장처리/완료 현황 건수, 기간·지역·상태 검색
- 상태 변경과 수정에 대한 감사 이력

### 제외 (1차)

- OCR 결과를 자동으로 최종 완료하는 기능
- 외부 문자·카카오 알림 발송
- 사진 속 주소를 지도 좌표로 자동 확정하는 기능
- 한 건을 여러 지역으로 분할 배정하는 기능

## 3. 용어와 상태

| 화면 표시 | 시스템 상태 | 의미 |
| --- | --- | --- |
| 미완료 | `registered` | OCR 검수 후 등록되었고 아직 현장처리가 없는 건 |
| 현장처리 | `field_processed` | 담당 매니저가 현장 처리내용을 저장한 건. 최종완료 대기 |
| 완료 | `completed` | 공무·팀장·관리자가 최종 완료 처리한 건 |
| 긴급 | `is_urgent=true` | 상태와 별개로 우선 처리 대상 |

`등록 → 현장처리 → 완료`만 허용한다. 완료 건은 재오픈 권한이 있는 사용자만 `현장처리`로 되돌릴 수 있으며, 사유를 반드시 남긴다. 이 규칙은 실수로 닫힌 건의 추적성과 통계 정확성을 지킨다.

## 4. 권한·지역 규칙

권한은 프런트엔드의 버튼 노출뿐 아니라 API와 DB 조회 조건에서 반드시 강제한다. 지역은 사용자 `region_id`와 이관 건의 `region_id`로 판정한다. 사용자의 지역이 없으면 업무이관 조회·처리 권한을 주지 않고 관리자에게 지역 지정 안내를 표시한다.

| 역할 | 조회 범위 | 등록 | 수정 | 현장처리 등록 | 최종 완료 | 완료 건 검색 |
| --- | --- | --- | --- | --- | --- | --- |
| 공무 (`public_official`) | 모든 지역 | 가능 | 모든 지역 | 가능 | 가능 | 모든 지역 |
| 관리자 (`admin`) | 모든 지역 | 가능 | 모든 지역 | 가능 | 가능 | 모든 지역 |
| 팀장 (`team_leader`) | 본인 지역만 | 본인 지역만 | 본인 지역만 | 가능 | 본인 지역만 | 본인 지역만 |
| 현장 매니저 (`manager`) | 본인 지역의 **미완료·현장처리**만 | 불가 | 불가 | 가능 | 불가 | 불가 |

- 현장 매니저에게는 완료 상태의 건을 API에서 반환하지 않는다. 따라서 목록·검색·직접 URL 모두에서 사라진다.
- 매니저의 현장처리는 자기 지역의 `registered` 건에만 최초 등록할 수 있다. `field_processed` 상태의 내용은 본인이 작성자일 때만 보완 수정할 수 있다. 다른 매니저의 처리내용을 덮어쓰지 않는다.
- 팀장이 여러 지역을 관리해야 하는 경우, 1차에서는 사용자별 `region_id` 하나를 기준으로 한다. 다지역 팀장 요구가 확정되면 별도 `user_regions` 연결 테이블로 확장한다.

## 5. 사용자 흐름

### 5.1 업무이관 등록 — 공무·팀장·관리자

1. 목록의 `업무이관 등록`을 누른다.
2. 등록자는 등록일시(기본값 현재), 지역(권한 범위 내 선택), 긴급 여부 체크박스를 입력한다.
3. `사진 등록`으로 이미지 1장 이상을 업로드한다. 원본은 파일 저장소에 보관하고 업로드자·시간·파일 해시를 저장한다.
4. 업로드 후 OCR을 비동기로 실행한다. 진행 중 상태를 보여주고, 실패 시 재시도·수동 입력을 제공한다.
5. OCR 결과를 수정 가능한 입력 영역에 표시한다. 시스템은 주소·처리요청 내용을 초안으로 분리하되, 사용자가 반드시 검수한다.
6. 사용자가 `저장 및 등록`을 누르면 필수값 검증 후 `미완료(registered)` 상태로 등록한다.
7. 목록에는 날짜, 지역, 주소, 처리내용, 긴급, 상태, 완료 버튼을 표시한다.

등록 시 필수값은 **지역, 주소, 처리내용, 사진 또는 수기 입력된 원문**이다. OCR 결과가 빈 경우에도 사진을 근거로 주소와 처리내용을 직접 입력하면 등록할 수 있다.

### 5.2 현장처리 — 현장 매니저 및 상위 권한

1. 사용자는 허용된 지역의 `미완료` 항목을 연다.
2. `현장처리 등록`에서 처리일시, 처리내용, 선택 사진을 입력한다.
3. 저장 시 상태는 `현장처리(field_processed)`가 되고 처리자·시간·내용이 이력에 기록된다.
4. 현장 매니저는 자신의 지역 건만 처리할 수 있으며 최종 완료 버튼을 볼 수 없다.

### 5.3 최종 완료 — 공무·팀장·관리자

1. `현장처리` 상태의 건에서 처리내용과 증빙을 확인한다.
2. `완료` 버튼을 누르고 완료 메모(선택)를 저장한다.
3. 상태가 `완료(completed)`로 전환되고 완료자·완료시각이 기록된다.
4. 해당 건은 현장 매니저의 목록에서 즉시 제외된다.

완료 전에는 현장처리 기록이 하나 이상 있어야 한다. 긴급 건도 같은 완료 검증을 적용한다. 단, 긴급 건의 선조치는 `긴급 선완료` 체크로 기록할 수 있으며, 이 경우에도 최종 완료는 상위 권한자의 명시적 완료 동작이 필요하다.

## 6. 화면·검색 요구사항

### 목록

- 상단 요약 버튼: `미완료 N`, `현장처리 N`, `완료 N`. 버튼 클릭은 해당 상태 필터를 즉시 적용한다.
- 기본 정렬: 긴급 우선 → 등록일시 내림차순. 사용자는 등록일시·최종처리일시 정렬을 선택할 수 있다.
- 필터: 기간(시작일~종료일), 상태, 지역(권한 내), 긴급 여부.
- 검색: 주소, 처리내용, OCR 원문, 등록자, 현장처리자.
- 매니저 화면에서는 지역 필터를 숨기고 본인 지역명만 고정 표시하며, 완료 탭과 완료 건수는 표시하지 않는다.
- 목록 행의 완료 버튼은 완료 권한자에게만 `field_processed` 상태에서 활성화한다. 그 외 상태 또는 권한에서는 비활성/숨김 처리한다.

### 상세

- 기본 정보: 등록일시, 지역, 긴급 여부, 주소, 처리요청 내용, 등록자.
- OCR 영역: 원본 사진 미리보기, 추출 원문, OCR 처리 상태·재시도.
- 현장처리 영역: 처리자, 처리일시, 처리내용, 처리 사진.
- 이력: 등록, OCR 수정, 현장처리, 최종완료, 재오픈의 행위자·시간·변경값·사유.

## 7. 데이터 모델 제안

기존 `work_transfers`를 확장해 기존 화면과 API의 호환성을 유지한다. 지역을 CELL로만 유추하지 않고 `region_id`를 직접 저장해 지역 없는 주소·CELL 변경에도 접근 규칙이 흔들리지 않게 한다.

### `work_transfers` 추가 열

| 열 | 설명 |
| --- | --- |
| `region_id` | 대상 지역 FK, 필수 |
| `workflow_status` | `registered`, `field_processed`, `completed` |
| `is_urgent` | 긴급 건 여부, 기본 `false` |
| `ocr_status` | `pending`, `processing`, `succeeded`, `failed` |
| `ocr_text` | 사진에서 추출한 원문 |
| `field_processed_at` | 최초 현장처리 저장 시각 |
| `field_processed_by` | 현장처리자 사용자 FK |
| `final_completed_by` | 최종 완료자 사용자 FK |
| `reopened_at`, `reopened_by` | 완료 재오픈 추적 |

주소와 처리요청 내용은 기존 `description` 및 호환 필드(`extra_json`)에서 분리해 명시 열로 이전하는 것을 권장한다. 마이그레이션 기간에는 기존 `status`를 유지하면서 `workflow_status`를 단일 진실 원천으로 사용하고, UI/API 응답에서 기존 상태값을 매핑한다.

### 별도 테이블

- `work_transfer_attachments`: 이관건 ID, 유형(`request_photo`/`field_photo`), 파일 URL, 원본 파일명, MIME, 크기, 해시, 업로더, 생성시각
- `work_transfer_field_actions`: 이관건 ID, 처리내용, 처리자, 처리시각, 사진 연결. 여러 차례의 현장 조치 이력을 보존
- `work_transfer_ocr_runs`: 첨부 ID, 엔진/버전, 상태, 추출 텍스트, 오류 코드, 시도 횟수, 실행시각. OCR 재시도와 품질 분석용

필수 인덱스: `(region_id, workflow_status, transfer_date DESC)`, `(workflow_status, completed_at DESC)`, `(is_urgent, workflow_status, transfer_date DESC)`, OCR 검색용 FTS 인덱스(주소·처리내용·OCR 원문).

## 8. API 요구사항

| API | 목적 | 권한 규칙 |
| --- | --- | --- |
| `GET /work-transfers` | 목록·요약 조회 | 서버가 역할·지역 조건을 추가 적용 |
| `GET /work-transfers/summary` | 상태별 건수 | 동일한 접근 조건과 기간/지역 필터 적용 |
| `POST /work-transfers` | 이관 등록 | 공무·관리자 전체 지역, 팀장 본인 지역 |
| `POST /work-transfers/:id/attachments` | 사진 업로드 | 등록·처리 권한 범위 내 |
| `POST /work-transfers/:id/ocr` | OCR 실행/재시도 | 등록 수정 권한자 |
| `POST /work-transfers/:id/field-actions` | 현장처리 등록 | 대상 지역 매니저 또는 상위 권한 |
| `POST /work-transfers/:id/complete` | 최종 완료 | 공무·관리자 전체 지역, 팀장 본인 지역 |
| `POST /work-transfers/:id/reopen` | 완료 재오픈 | 공무·관리자 (사유 필수) |
| `PUT /work-transfers/:id` | 등록 정보 수정 | 등록·수정 권한 범위 내, 완료 후 핵심값 변경 금지 |

모든 변경 API는 권한 오류 시 `403`, 타지역 리소스는 존재 여부 노출을 막기 위해 `404`를 반환한다. 목록의 `limit`·페이지네이션은 서버에서 처리하며, 클라이언트 필터만으로 접근 제한을 구현하지 않는다.

## 9. OCR·사진 처리 요구사항

- 지원: JPG, PNG, HEIC(서버 변환 가능 시), PDF 첫 페이지. 파일당 최대 크기와 장수는 운영 환경 기준으로 설정한다.
- 업로드 직후 바이러스/형식 검증, EXIF 위치정보 제거 옵션, 원본 접근은 인증된 사용자로 제한한다.
- OCR은 큐 기반 비동기 작업으로 실행한다. 화면 새로고침 후에도 상태를 조회할 수 있어야 한다.
- OCR 결과는 자동 확정하지 않는다. 사용자가 수정한 주소·처리내용과 OCR 원문은 별도로 보관한다.
- 실패해도 업무 등록을 막지 않는다. 실패 상태·오류 사유·재시도 버튼을 제공하고 수기 입력을 허용한다.

## 10. 검증 기준 (수용 기준)

1. 공무와 관리자는 모든 지역 건을 등록·수정·현장처리·완료·검색할 수 있다.
2. 팀장은 본인 `region_id`가 아닌 건의 목록·상세·API 접근을 할 수 없고, 본인 지역에서는 동일 작업을 수행할 수 있다.
3. 매니저는 본인 지역의 미완료/현장처리 건만 보며, 타지역·완료 건의 직접 URL/API 접근도 실패한다.
4. 사진 업로드 후 OCR 성공·실패·재시도·수기 보정 흐름이 모두 작동하고, OCR 원문과 최종 저장 텍스트가 구분 보관된다.
5. 현장처리 기록 없이 완료 요청하면 검증 오류가 발생한다.
6. 완료 성공 시 완료자·완료시각·이력이 남고, 매니저 목록 및 요약에서 즉시 제외된다.
7. 상태별 건수는 사용자가 볼 수 있는 데이터와만 일치하며, 기간 필터를 적용하면 같은 조건으로 다시 계산된다.
8. 긴급 건은 목록에서 우선 표시되고, 모든 상태 전환 이력에 긴급 여부가 남는다.

## 11. 구현 우선순위

1. **권한·지역 기반 조회/상태 전환**: 데이터 마이그레이션, API 정책, 목록 필터, 요약 건수.
2. **현장처리·최종 완료 화면**: 상태 전이 검증, 이력·첨부 구조, 매니저 완료 건 숨김.
3. **사진 업로드와 OCR**: 저장소 연결, 비동기 OCR, 결과 검수 UI.
4. **운영 보강**: 재오픈, 알림, SLA(긴급 미처리 경과), OCR 품질 지표.

## 12. 추가 제안

- **긴급 SLA 표시**: 긴급 등록 후 설정 시간 내 현장처리가 없으면 목록에 경과 시간을 붉게 표시한다. 자동완료가 아닌 우선순위 판단 용도다.
- **완료 전 체크리스트**: 주소·처리내용·현장처리자·처리시각·사진(운영 정책상 필요 시)을 확인해야 완료 버튼이 활성화되도록 해 부실 종료를 줄인다.
- **권한 변경 감사**: 사용자의 지역 또는 역할 변경도 별도 감사 로그에 남긴다. 권한 변경 후 과거 데이터의 접근 범위를 설명할 수 있다.
- **일일업무 연계는 2차**: 현장처리 완료 시 일일업무 초안을 제안할 수 있으나, 중복 집계를 막기 위해 사용자의 확인 후에만 생성한다.

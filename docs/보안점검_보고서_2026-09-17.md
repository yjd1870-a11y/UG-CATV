## 2026-09-18 배포 후보 재점검 결과

9월 17일 보고서의 세 가지 배포 차단 후보를 현재 코드로 다시 확인했다. **타 지역 자재 거래 조회·상세·수정·삭제·취소는 역할 및 지역 범위 정책에 맞게 차단되고, 일반 사용자의 과거 일일업무 날짜 변경 우회도 차단됐다.** 신규 자재관리는 백엔드·프런트 기능 플래그가 기본 OFF인 dark launch 상태다.

| 기존 발견 | 현재 판단 | 근거 |
|---|---|---|
| 팀장의 타 지역 자재 거래 취소 | 해결 | 취소·수정·삭제가 동일한 가시성/지역 검사를 사용하며 `test:inventory`에서 타 지역 접근을 회귀 검증 |
| 일반 사용자의 과거 일일업무 날짜 변경 우회 | 해결 | 저장된 원래 날짜와 요청 날짜를 모두 검사하며 `test:daily-work-permissions`에 과거→오늘 변경 재현 추가 |
| 자재 목록·상세의 타 지역 노출 | 해결 | 현재 역할 정책에 따른 목록/상세 범위 적용 및 관리자·공무·팀장·매니저 교차 테스트 통과 |

추가로 업무이관 완료는 master와 thumbnail을 HTTP 요청 안에서 즉시 삭제한 뒤에만 completed로 커밋한다. 삭제 대상과 객체별 결과는 전용 강한 기록 테이블에 남고, 저장소 삭제 실패 시 `PHOTO_PURGE_FAILED`로 완료를 중단한다. 일반 `writeAuditLog`가 실패를 기록만 하고 기존 기능 요청은 유지하는 동작은 호환성을 위해 바꾸지 않았으며, 재고 거래의 `inventory_audit_logs`는 거래와 같은 SQLite 트랜잭션에서 필수 성공한다.

운영 R2의 실제 공개 설정, CORS, lifecycle, 객체 수·용량 및 DB/R2 불일치는 읽기 전용 자격증명이나 Dashboard 내보내기가 없어 아직 검증하지 못했다. 이 항목은 운영 반영 승인 전 필수 확인 사항이다.

아래 내용은 9월 17일 최초 발견 당시의 기록이며, 현재 상태와 혼동하지 않도록 역사적 재현 자료로 보존한다.

## 판단

이번 확인 범위에서는 **로그인 없이 관리자 권한을 얻거나 전체 자료를 가져가는 치명적(Critical) 취약점은 확인되지 않았습니다.** 다만 권한 제한을 우회하는 문제 2건을 임시 환경에서 재현했으며, 조회 범위가 일관되지 않은 문제 1건을 추가로 확인했습니다. 이는 서비스 전체가 안전하다는 인증이나 침해 이력이 없다는 의미는 아닙니다.

가장 먼저 고칠 것은 **신규 자재관리에서 팀장이 다른 지역의 거래를 취소할 수 있는 문제**입니다. 신규 자재관리 배포 전에 수정하는 것이 좋습니다.

| 우선순위 | 발견 내용 | 업무상 영향 | 확인 범위 |
|---|---|---|---|
| 1 · 높음 | 팀장이 담당지역 밖의 자재 거래를 취소할 수 있음 | 타 지역의 정상 거래와 재고 집계를 잘못 바꿀 수 있음 | 로컬 코드·임시 DB 재현. 운영의 신규 자재관리 주소는 404 응답 |
| 2 · 중간 | 일반 사용자가 과거 일일업무 수정 잠금을 우회할 수 있음 | 이전 실적을 오늘로 옮기고 건수를 바꿔 과거·현재 집계를 왜곡할 수 있음 | 로컬 코드·임시 DB 재현. 운영 계정으로 변경 요청은 하지 않음 |
| 3 · 정책 확인 필요 | 일반 계정이 다른 지역의 자재 거래 목록·상세를 볼 수 있음 | 업무주소, 작업자, 사용내역 등 불필요한 정보가 공유될 수 있음 | 로컬 재현. 전체 직원 공개가 의도라면 취약점으로 확정하지 않음 |

## 1. 팀장이 다른 지역의 자재 거래를 취소할 수 있음

쉽게 말하면, 다른 팀의 자료를 고치는 것은 막아 놓았지만 **같은 자료를 취소하는 문에는 지역 확인이 빠져 있습니다.**

임시 환경에 서로 다른 지역의 팀장과 거래를 준비했습니다. 팀장이 타 지역 거래를 수정하려 하면 정상적으로 거절됐지만, 취소 기능으로 요청하자 성공했고 원래 거래가 취소 상태로 바뀌었습니다. 관리자 계정을 빼앗을 필요 없이 기존 팀장 계정만 있으면 가능한 경로입니다.

- 재현 결과: 일반 수정은 403 `REGION_SCOPE_FORBIDDEN`, 취소는 201 성공, 원거래 상태는 `REVERSED`.
- 영향: 다른 지역 거래를 무효화해 재고·사용량 집계의 신뢰성을 해칠 수 있습니다. 감사 기록은 남지만 변경 자체를 막지는 못합니다.
- 조치: 취소 전에 해당 거래의 지역과 로그인한 팀장의 담당지역을 비교해야 합니다. 수정·삭제·취소 기능에 동일한 지역 검사 규칙을 적용하고, 일괄등록·엑셀 출력도 같은 기준으로 검토해야 합니다.
- 위치: `backend/routes/inventory.ts:331`, `backend/inventory-service.ts:404`. 정상적인 지역 검사와 비교할 위치는 `backend/inventory-service.ts:461`입니다.
- 운영 반영 여부: 사이트의 `/api/material-management/bootstrap`은 점검 당시 404 `NOT_FOUND`였습니다. 해당 파일들도 작업 폴더의 미커밋 신규 기능으로 확인됐습니다. 따라서 **현재 운영 사이트에서 이미 악용 가능하다고 단정하지 않습니다.**

## 2. 과거 일일업무 수정 잠금을 날짜 변경으로 우회할 수 있음

일반 사용자에게는 오늘 업무만 수정하도록 제한돼 있습니다. 그런데 서버가 원래 기록의 날짜 대신 **사용자가 새로 보낸 날짜**를 기준으로 권한을 판단합니다.

임시 환경에서 일반 사용자가 자신의 과거 기록을 수정하면 거절됐습니다. 같은 기록에 날짜를 오늘로 바꾸고 건수를 수정해 보내면 저장됐습니다. 화면의 버튼이 막혀 있어도 서버가 요청을 받아들이는 문제입니다.

- 재현 결과: 과거 기록의 일반 수정은 403 `PAST_WORK_LOCKED`. 날짜를 오늘로 함께 변경하면 200 성공. 2020-01-20의 1건 기록이 2026-09-17의 9건 기록으로 바뀌었습니다.
- 조건: 본인의 과거 업무 기록이 있어야 하고, 오늘의 동일 집계 기록과 충돌하지 않아야 합니다. 타인의 업무까지 수정하는 문제는 아닙니다.
- 영향: 이전 날짜의 실적이 빠지고 오늘 실적이 달라져 보고자료의 신뢰성이 떨어집니다.
- 조치: 원래 저장된 날짜와 변경하려는 날짜를 모두 검사해야 합니다. 일반 사용자에게는 과거 기록을 오늘로 옮기는 변경도 차단해야 합니다.
- 위치: `backend/routes/daily-work.ts:272`, 특히 275~277행. 오늘만 수정하도록 제한한 규칙은 72행에 있습니다.
- 운영 반영 여부: 운영 서버의 배포 코드·계정을 확보해 재현한 것은 아니므로 운영에서도 동일한지는 추가 확인이 필요합니다.

## 3. 자재 통계와 거래 목록의 조회 범위가 서로 다름

일반 사용자의 자재 통계는 자기 업무로 제한하지만, 별도의 거래 목록·상세에서는 다른 지역 기록도 반환합니다. 같은 사용자로 통계에서는 0건이 보이는데 목록과 상세에서는 타 지역의 시험 거래가 조회되는 것을 확인했습니다.

- 재현 결과: 다른 지역 거래의 목록·상세 모두 200 성공. 담당자 이름, 업무주소, 사용목적 등 거래정보가 반환됩니다.
- 판단: **“일반 직원은 본인 내역만 조회”가 운영 방침이라면 수정해야 할 권한 누락입니다.** 전사 자재내역 공개가 의도된 기능이라면 이 항목은 취약점으로 분류하지 않아야 합니다. 코드만으로 운영 방침을 확정할 수 없어 별도 구분했습니다.
- 조치: 회사의 조회 방침을 정한 뒤 초기화 데이터, 목록, 상세, 통계, 엑셀에 같은 기준을 적용합니다. 화면에서 숨기는 방식으로는 해결되지 않습니다.
- 위치: `backend/routes/inventory.ts:52`, `:77`, `:118`; `backend/inventory-service.ts:386`, `:897`. 제한된 통계 처리와 비교할 위치는 `backend/inventory-service.ts:927`입니다.
- 운영 반영 여부: 신규 자재관리 기능으로, 이번 운영 요청에서는 확인되지 않았습니다.

기존 `security.integration`, `guest-permissions`, `daily-work-permissions` 테스트는 각각 분리된 임시 DB에서 통과했습니다. 다만 이 테스트들의 통과가 위에서 새로 재현한 우회 경로까지 차단한다는 뜻은 아닙니다.

## 권장 처리 순서

1. 신규 자재관리 배포 전에 타 지역 거래 취소를 차단합니다.
2. 일반 사용자의 과거 일일업무 날짜 변경을 차단하고 운영 배포본에도 같은 문제가 있는지 확인합니다.
3. 자재 거래의 공개 범위를 결정하고 모든 조회 경로에 통일합니다.
4. 위 재현 사례를 회귀 테스트에 포함한 뒤 배포합니다.

## 범위와 제한

- 실제 사이트에서는 소수의 읽기 요청으로 확인했습니다. 운영 계정 생성, 비밀번호 추측, 업무 데이터 변경·삭제, 부하 공격은 수행하지 않았습니다.
- 변경을 수반하는 재현은 새로 만든 `.tmp/security-audit/` 아래의 독립 DB와 저장소에서만 수행했습니다. 원래 업무 DB와 애플리케이션 코드는 수정하지 않았습니다.
- 클라우드 관리 콘솔, 운영 비밀값, 과거 침해 로그, R2의 실제 공개 설정 전체는 직접 검증하지 않았습니다. 로그인 후 운영 기능에 대한 평가는 로컬 코드 분석과 분리해서 해석해야 합니다.
- 요청에 따라 동명이인 등 특수 조건에 의존하는 문제와 낮은 위험의 개선사항은 주요 발견에서 제외했습니다.
- 라이브러리의 알려진 취약점 자동조회(`npm audit`)는 의존성 메타데이터의 외부 전송을 이유로 자동 승인 검토에서 실행이 거절됐습니다. 따라서 라이브러리에 알려진 취약점이 없다고 판단하지 않았습니다. 추가 실행에는 패키지 이름·버전 등 의존성 정보의 npm 서비스 전송 승인이 필요합니다.
